# Mini-Wiki 3.3 内容提示词

这些提示词用于填充 `mini-wiki:content` 区域。CLI 已负责扫描、Properties、关系、导航、Bases、Canvas、
搜索索引和 Manifest；Agent 的职责是把仓库证据解释成准确、可维护的专业知识。

## 通用约束

把下面约束附加到每个生成任务：

```text
你正在补充 Mini-Wiki 托管页面的 Agent 内容区域。

必须：
1. 先读取 build-plan、analysis、graph 和目标源码，再写结论。
2. 所有事实都能追溯到仓库相对路径；对关键结论给出窄范围的相对 Markdown 链接。
3. 说明证据证明的行为、边界或关系，不能只罗列链接。
4. 解释 WHY、HOW、输入输出、失败路径和恢复方式。
5. 链接相关 Wiki 页面，形成知识网络。
6. 只在关系或时序复杂时使用 Mermaid；推断必须显式标记。
7. 证据不足时写“待验证”，并给出可执行的验证步骤。
8. 只修改 mini-wiki:content 区域，保留 Properties、生成区、未知属性和用户内容。

禁止：
- 虚构文件、符号、接口、行为、行号或运行结果；
- 写入绝对机器路径或本地 URL；
- 以固定字数、固定图表数制造填充内容；
- 复制生成区已经表达的清单而不提供解释；
- 执行 Mini-Wiki 插件携带的脚本、命令或代码。
```

源码证据格式：

```markdown
- [src/auth/session.py:41-79](../../../src/auth/session.py#L41-L79) — 会话校验先检查签名，再检查撤销状态。
```

根据页面深度调整 `../` 层级，确保链接从当前页面可解析。

## 模块页面

```text
目标：为 {{MODULE_NAME}} 编写可供维护者使用的模块说明。

输入：
- 文档 ID：{{DOCUMENT_ID}}
- 源文件：{{SOURCE_PATHS}}
- 图谱邻居：{{GRAPH_NEIGHBORS}}
- 已有用户内容：{{EXISTING_CONTENT}}

分析步骤：
1. 找出真实入口、公开接口、核心类型和装配位置。
2. 沿一条主要调用链追踪输入、状态变化、输出和异常。
3. 区分本模块职责、上游前置条件和下游副作用。
4. 检查配置、持久化、并发、缓存、权限和回滚边界。
5. 用图谱邻居核对依赖关系，不能把“同目录”当成“有依赖”。

输出建议：
- 职责与非职责
- 入口与公开契约
- 关键流程
- 状态与数据模型
- 依赖和消费者
- 失败、恢复与边界条件
- 安全和性能注意事项
- 扩展指南
- 源码证据与相关页面

只输出内容区域正文，不输出 YAML 或所有权标记。
```

## 架构页面

```text
目标：基于仓库实际装配和依赖，解释 {{PROJECT_NAME}} 的架构。

要求：
1. 从运行入口追踪到领域、基础设施和外部系统。
2. 区分编译期依赖、运行期调用、数据流和部署关系。
3. 指出架构边界由哪些接口、配置或目录约定实施。
4. 至少解释一个关键请求或任务的端到端路径。
5. 记录错误如何传播、在哪里重试、在哪里持久化、如何观测。
6. 若 Mermaid 能显著降低理解成本，绘制一个证据化架构图；每条关键边都能回到源码。
7. 将高风险推断放入“待验证”而不是写成确定事实。

输出：架构摘要、边界、主要流程、数据与状态、横切关注点、演进约束、证据索引和相关页面。
```

## API 页面

```text
目标：记录 {{API_NAME}} 的真实公开契约，而不是从名称猜测。

逐项核对：
- 路由或导出位置；
- 身份、权限和租户边界；
- 参数类型、默认值、校验和规范化；
- 成功响应、错误响应和副作用；
- 幂等、分页、限流、超时和重试；
- 兼容性与弃用策略；
- 能由测试或调用方证明的示例。

对每个端点/方法给出紧邻源码的相对链接。示例必须与实现一致，不得编造响应字段。
```

## 源文件页面

```text
目标：解释 {{SOURCE_PATH}} 为什么存在，以及它在知识图谱中的角色。

避免逐行复述。聚焦：
1. 文件的职责和生命周期；
2. 关键符号如何协作；
3. 被谁调用、调用谁；
4. 哪些更改会破坏外部契约；
5. 关联测试覆盖了什么、未覆盖什么；
6. 适合继续阅读的模块与架构页面。
```

## 质量补强

用于 `quality.base` 中质量不足或过期页面：

```text
页面：{{DOCUMENT_PATH}}
质量状态：{{QUALITY}}
新鲜度：{{FRESHNESS}}
源码漂移：{{SOURCE_DRIFT}}

任务：比较页面正文、当前源码、测试和图谱关系。列出已证实仍正确、已过期、缺失和无法验证的内容；
然后只修改内容区域，优先修复会误导维护者的契约、流程和风险说明。不要因为状态为 stale 就重写仍正确的段落。
```

## 孤立页面治理

用于 `orphans.base`：

```text
页面：{{DOCUMENT_PATH}}
图谱邻居：{{GRAPH_NEIGHBORS}}

判断孤立原因：确实无关联、图谱漏检、缺少页面链接、还是应归档。只有源码证据支持时才新增关系或链接；
如果页面已失效，建议通过 Mini-Wiki 的可恢复归档流程处理，不能直接删除。
```

## Canvas 解释校对

Canvas 由 CLI 确定性生成，Agent 不直接编辑派生 JSON。校对时使用：

```text
对照 graph.json 与 {{CANVAS_NAME}}：
1. 核对关键节点和边是否反映真实架构/领域/追溯关系；
2. 识别聚合造成的信息损失；
3. 将问题归因到扫描、图谱或元数据，而不是手改 Canvas；
4. 修复事实源后重建，并用严格校验确认文件节点与边有效。
```

## Bases 工作队列

Bases 是 Properties 的视图，不是独立数据源。对视图中的任务使用：

```text
从 {{BASE_NAME}} 选择 {{FILTER_DESCRIPTION}} 的页面。逐页读取真实 Properties 与源码；完成内容补强后运行
build 和 check --strict，让状态、新鲜度、质量、孤立标记和反向链接数由统一流水线刷新。不要手工维护
另一份状态清单。
```

## 完成复核

```text
在报告完成前确认：
- 第二次构建没有无法解释的差异；
- strict 校验无结构错误；
- 中文和英文关键查询都能找到目标页面；
- 所有关键结论都有可解析的仓库相对证据；
- 用户内容、未知 Properties 和未托管页面保持不变；
- 未执行插件代码，也未在未授权情况下打开或探测 Obsidian。
```
